## Validation boundaries

On 24 November 2026, a clean Home Assistant 2026.11.2 installation used **Marketplace → Add from link**, selected the named public **v1.0.0** release and registered the dashboard module. The card, licence and manifest matched all three published files on disk and over HTTP. The release tag also passed all eight [HACS plugin checks](https://github.com/senyo888/thermal-intelligence/actions/runs/45459007561).

On 23 November 2026, Home Assistant 2026.11.2 upgraded an existing Marketplace installation to the card from [`a123d47`](https://github.com/senyo888/thermal-intelligence/commit/a123d4720f216556d0c6bff177963a37e39404b0). The resource kept its ID. The installed files and the files served over HTTP matched the card and GPL licence checksums above.

In a fresh Chromium session, three saved thermostat cards showed the same current and target temperatures as Home Assistant. All three still matched after a reload at phone width. Cancelling a top-row icon edit restored the saved selection. The visual editor showed all four humidity thresholds on one bar. Thermostat requests, control ownership and saved settings stayed intact. This run covered installation and display. The room-command and 48-hour soak results below belong to the earlier build.

The earlier candidate passed 203 unit, 227 synthetic browser, 14 foundation, 18 package and eight Marketplace checks. Browser coverage includes the committed stable module, beta/RC identities, legacy coexistence, configuration preservation and phone/tablet/desktop fixtures. An independent in-memory build reproduced the module exactly.

The following control, rollback and soak results cover the earlier 265,844-byte module from `03df08e`. Editor save/reload, room controls and a five-minute scheduled Boost with automatic return passed. A whole-house Boost was confirmed in seven of eight rooms. One user-locked thermostat kept its original target and the card reported Unknown after the confirmation timeout. All eight rooms returned to their starting settings. The trials verified reported requests and controls. The 48-hour Lab observation finished on 22 November 2026 with all nine checkpoints healthy. It covered Home Assistant Core, the served 1.0.0 module, the VT provider and the expected HA/VT versions. See [compatibility](compatibility.md#100-package).

On Home Assistant 2026.11.2, Marketplace rolled an installed 1.0.0 back to RC.4 and reinstalled the exact 1.0.0 module. Each version matched on disk, over HTTP and in a fresh browser. The existing resource ID survived both changes. Removal cleared the module and preserved the saved dashboard and unrelated resource.

Before publication, a separate Marketplace rehearsal selected the three assets from a simulated v1.0.0 listing. The clean install above verified the public release.

When testing an explicit development commit, a clean install could fetch the module from the default branch or pick up a historical file with the same name. The prepared layout gives the old fixture a unique filename, and the nine offline Marketplace checks cover this packaging rule. For a community install, choose the published release.

Run either command from a clone containing the tagged commit. Both reproduce the released card and licence. Use `--marketplace` to reproduce the published manifest, which also records the Dashboard distribution metadata.

```sh
python3 -B scripts/package_release.py --commit 4e6b9416be04e75a3a3ecf90117ab5f5958f61e0 --output /tmp/ti-1.0.0-manual
python3 -B scripts/package_release.py --commit 4e6b9416be04e75a3a3ecf90117ab5f5958f61e0 --marketplace --output /tmp/ti-1.0.0-marketplace
```

The output directories must not already exist. The manifest's intended delivery branch is `main`; generating it does not promote a branch, create a tag or publish a release.
